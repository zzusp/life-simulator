# Feature Specification: 全局 UI/UX 重设计

**Feature Branch**: `002-ui-ux-redesign`  
**Created**: 2025-10-27  
**Updated**: 2025-10-27  
**Status**: Completed  
**Input**: User description: "修改UI，要求类似于手绘卡通风格的效果（参考图片：带有纸张质感、手绘字体、卡通按钮边框）"

**Note**: 本规范已基于实施经验进行增强，新增了流程与质量保证要求（FR-012 至 FR-017）以及相应的验收标准和成功指标，旨在指导未来类似项目避免常见陷阱并提高实施效率。

## 目标与范围

- 目标：建立一致、易用、沉浸的视觉与交互体系，覆盖首页、游戏主页（类型选择）、游戏进行页（场景/选择/分数反馈）、结果页、分享页、历史页、测试页的展示、风格、布局、状态、动效与可达性。
- 范围内：视觉与交互规范、布局与排版体系、状态与反馈、动效节奏、空/错/慢态、无障碍、国际化基线、文案语气基线。
- 范围外：后端逻辑、AI 模型能力、数据库结构、性能优化与监控实现细节。

## 假设

- 面向中文用户，移动端优先，桌面优先支持 1280px 以上屏幕。
- 玩家以匿名使用为主，无登录流程；分享内容公共可见且不含敏感隐私。
- **以手绘卡通风格为主题**：温暖色调、手绘笔触、纸张质感、卡通图标、圆润边框、趣味性排版。

## User Scenarios & Testing (mandatory)

### User Story 1 - 新手从首页开始游戏 (Priority: P1)

首页清晰展示游戏价值，1 次点击进入游戏主页并完成类型选择，视觉引导明显。

**Why this priority**: 入口转化直接影响整体留存与游玩率。

**Independent Test**: 仅改造首页与游戏主页，观察从首页到开始游戏的转化率是否提升。

**Acceptance Scenarios**:

1. Given 首次到访首页，When 浏览主标题与 CTA，Then 3 秒内理解玩法并发现“开始游戏”按钮。
2. Given 点击“开始游戏”，When 进入游戏主页，Then 可在 2 次以内交互完成类型选择并开始。

---

### User Story 2 - 玩家在场景中做出选择并获得清晰反馈 (Priority: P1)

游戏进行页提供清晰的场景标题、描述、选择卡片、禁用态与加载反馈，分数变化与成就以非打断式方式展示。

**Why this priority**: 决策体验是核心乐趣，反馈的清晰与节奏决定沉浸感。

**Independent Test**: 仅替换场景页 UI 与动效，验证玩家在 1 分钟内完成 3 次选择且无迷惑。

**Acceptance Scenarios**:

1. Given 场景已加载，When 悬停/触碰某个选择，Then 卡片出现高亮与可点击提示，辅助文案可见。
2. Given 点选一个选择，When 进入处理状态，Then 其他选项禁用且出现半透明遮罩+进度反馈。
3. Given AI 返回结果，When 分数变化，Then 1s 内完成数字过渡动画并显示变化值与新分数标签。
4. Given 解锁成就，When 出现成就 Toast，Then 3s 内自动淡出，不遮挡主交互区。

---

### User Story 3 - 完成一局并查看结果/分享 (Priority: P2)

结果页以标题+摘要+关键统计（分数/选择数/时长）+人生类型信息展示，提供“重新开始/查看历史/分享结果”。

**Why this priority**: 促进闭环与传播，提升复玩与外部流量。

**Independent Test**: 仅替换结果页与分享页样式，观察分享点击率与回流率。

**Acceptance Scenarios**:

1. Given 游戏结束，When 打开结果页，Then 结果标题与原因文案在首屏可见，关键统计以卡片栅格呈现。
2. Given 点击分享，When 复制链接成功，Then 显示轻量反馈；失败时显示重试与引导文案。

---

### User Story 4 - 访问他人分享页并理解结果 (Priority: P3)

分享页展示该局概览、成就列表与引导 CTA 回到首页开始游戏。

**Independent Test**: 仅改造分享页，抽样用户可在 5 秒内说出该局主题与成绩高低。

**Acceptance Scenarios**:

1. Given 有效分享链接，When 打开分享页，Then 看到清晰的分数色阶与标签（优秀/良好等）。
2. Given 无效链接，When 加载失败，Then 显示错误页与返回首页的次要 CTA。

---

### User Story 5 - 无障碍与键盘可用性 (Priority: P2)

全站支持键盘导航、焦点可视、语义结构与对比度，动效可降级。

**Independent Test**: 使用仅键盘完成一局；在“减少动态效果”开启时，动效替换为非运动反馈。

**Acceptance Scenarios**:

1. Given 键盘导航，When Tab 遍历，Then 焦点顺序与视觉提示合理，Enter/Space 可触发主要操作。
2. Given 系统设置减少动态，When 触发动效，Then 使用淡入淡出与数值瞬时更新，无大位移动画。

### Edge Cases

- 极慢网络或 AI 返回延迟：加载骨架屏+线性进度占位，超过 10 秒提供“继续等待/取消”选项。
- 文案超长：标题/描述多行截断策略与“展开全文”交互；选择文本 2 行截断并提供完整查看。
- 分数极值抖动：频繁加减分时节流展示，合并多次微小变化为一次动画。
- 分享失败：剪贴板权限不足时，提供可选“手动复制”输入框与一键全选。
- 成就短时间内大量解锁：采用严格串行队列（并发=1），条间≥300ms，避免轰炸与遮挡。
- API 短暂失败（历史列表/详情）：10s 超时或 4xx/5xx 错误时显示内嵌错误区块；“重试”保留 lastCursor 并去重；429/503 提示服务繁忙并允许稍后重试；不跳全屏错误页。

## Requirements (mandatory)

### Functional Requirements

- FR-001 设计系统：
  - 建立色彩（主色米黄/深蓝/木棕，辅色暖橙/浅蓝，语义色柔和绿/黄/红）、字号层级（h1 手写体≥36px，h2-h6 及正文楷体 16-24px，说明≥14px）、间距与圆角（圆角 12-24px）、阴影（多层立体）规范；
  - 定义卡片（纸张质感+边框）、按钮（立体阴影+弹跳）、标签、徽章、进度、Toast、空状态的视觉与交互状态（默认/悬停/按下/禁用/加载）。
- FR-002 布局与响应：
  - 12 栅格布局基线；移动单列、平板双列、桌面三列优先；容器最大宽度与安全留白规范；
  - 关键页面首屏信息密度可控，主要 CTA 始终在可视区域内。
- FR-003 场景与选择：
  - 场景标题+描述区域与选择列表区分明显；选择卡片支持高亮、辅助文案与禁用态；
  - 选择处理态出现半透明遮罩与进度指示，不可重复提交。
- FR-004 反馈与动效：
  - 分数变化采用数字平滑过渡（约 1s）、色彩强化；
  - 成就以角落 Toast 队列淡入淡出（单条 3s，队列并发=1 严格串行），不阻塞主要操作；
  - **手绘卡通风格动效**：默认 300–400ms；采用弹性曲线 cubic-bezier(0.68, -0.55, 0.265, 1.55)（bounce）或标准 ease-out；位移≤16px，缩放幅度≤5%；支持轻微摇摆（wiggle）和弹跳（bounce）效果；
  - 尊重系统"减少动态效果"，提供无运动替代方案（颜色/对比/微振动）。
- FR-005 可达性：
  - 文本与背景对比度至少达到 WCAG AA；
  - 键盘可操作性（焦点环可见、顺序正确、跳过到主要内容）；
  - 图标/颜色不可单一承载信息，提供文字/形状冗余编码。
- FR-006 文案与语气：
  - 核心文案风格统一，提示/错误/分享文案模板化；
  - 结果页根据结局类型提供差异化标题与描述，不使用负面攻击性语言。
- FR-007 空/错/慢态：
  - 为“无网络/AI 繁忙/分享失败/无成就”提供插画/图标+说明+操作；
  - 骨架屏用于列表与卡片加载；错误态统一为内嵌错误区块（图标+标题+说明+重试按钮+次要 CTA 返回首页）。
- FR-008 国际化与多语：
  - 首版仅中文，不交付英文界面与文案；
  - 为后续多语扩展预留文案长度与截断策略。
- FR-009 品牌与主题：
  - **默认主题为"手绘卡通+浅色方案"**：温暖色调（米黄+深蓝+木棕）、纸张质感背景、圆润边框、立体按钮（多层阴影）；
  - **字体策略**：页面主标题（h1）使用手写体站酷快乐体以体现趣味性；所有正文、按钮文字、标签、辅助说明使用楷体霞鹜文楷以确保可读性；移动端字号适当增大（标题≥24px，正文≥16px），行距≥1.75；
  - **装饰元素策略**：适度使用回形针、标签纸、钉子等装饰；主要页面（首页、游戏主页、场景页、结果页、分享页）使用装饰增强氛围，列表页（历史列表）和表单类功能页面简化装饰保持简洁与可读性；
  - 首版不提供深色主题与主题切换。
- FR-010 法规与隐私呈现：
  - 分享页不展示个人可识别信息；
  - 若含用户生成文本，提供内容审核失败的用户可见反馈。
- FR-011 历史页与详情：
  - 历史页提供列表：时间、人生类型、分数（含色阶/标签）、成就数量、时长；
  - 支持按时间倒序与无限滚动加载；
  - 无限滚动触发阈值：距底部 300px 内触发；请求参数 limit 默认 20（最小 10，最大 50）；
  - 触发节流：300ms；显示底部加载占位；超时 10s 显示内嵌错误区块并可重试；
  - 重试策略：沿用 lastCursor，无重复项（以 sessionId 去重）；429/503 显示"服务繁忙，请稍后再试"。
  - 详情页提供标题+摘要+逐步选择（文本+分数变化标签），并包含关键节点概览；
  - 无数据时展示空状态与引导 CTA。

#### 流程与质量保证要求（基于实施经验）

- FR-012 设计对齐与交付物：
  - **视觉参考必要性**：设计阶段必须提供 2-3 个具体视觉参考（截图、设计稿、竞品示例），不可仅依赖文字描述；
  - **设计走查**：实施前进行设计对齐会议，确认配色、布局、组件样式、交互细节等具体视觉标准；
  - **交付物清单**：提供完整的设计规范文档，包括色板、字体、间距、圆角、阴影、动效参数等可直接应用的数值；
  - **原型验证**：关键页面需提供可交互原型或高保真设计稿，在实施前获得确认。

- FR-013 设计简洁性原则：
  - **简洁优先**：优先实现清晰的配色、布局、卡片、按钮等基础视觉元素，避免过度设计；
  - **复杂度约束**：限制单页面的动效数量（≤3 种动效类型）、阴影层级（≤2 层）、渐变使用（避免多色渐变）；
  - **装饰适度**：装饰元素（3D 变换、粒子效果、复杂纹理）需明确业务价值，否则不引入；
  - **渐进增强**：从最简单版本开始实施，基于用户反馈决定是否增加装饰性效果。

- FR-014 技术基础设施验证：
  - **工具链检查**：实施前验证 PostCSS、Tailwind CSS、CSS Modules 等样式工具配置完整且工作正常；
  - **测试页面**：创建独立的样式测试页面，验证边框、圆角、阴影、颜色等基础样式可正常渲染；
  - **缓存清理**：提供清理构建缓存（`.next`、`node_modules/.cache` 等）和浏览器缓存的标准流程；
  - **环境一致性**：确保开发、预览、生产环境的样式渲染一致，避免环境差异导致的样式问题。

- FR-015 验收流程与反馈机制：
  - **分阶段验收**：按页面/模块进行分阶段验收，每个阶段提供预览链接或截图确认；
  - **反馈响应**：对所有用户反馈（包括"不满意"等模糊反馈）进行响应，主动请求具体澄清；
  - **视觉确认**：通过截图或实时预览确认双方看到相同效果，排除缓存或环境差异；
  - **变更记录**：记录每次基于反馈的调整内容，避免循环修改和方案反复。

- FR-016 迭代开发里程碑：
  - **快速原型**：首次实施在 1-2 天内完成可交互原型，尽早收集反馈；
  - **预留调整**：为基于反馈的调整预留至少 30% 的开发时间；
  - **方案灵活性**：准备好基于反馈推翻现有方案，不固守初始实现；
  - **里程碑定义**：M1-基础视觉（配色+布局+组件），M2-交互与动效，M3-细节打磨与优化。

- FR-017 代码质量与维护：
  - **测试文件清理**：完成实施后删除所有测试页面、调试组件、临时工具文件；
  - **静态资源优化**：清理未使用的图片、字体、SVG 等静态资源，修复 404 错误；
  - **废弃代码移除**：删除被替换的旧组件、废弃的样式文件、过时的配置；
  - **文档维护**：生成清理报告、更新实施文档、记录废弃方案以避免重复尝试；
  - **Linter 检查**：确保无 ESLint/TypeScript 错误，控制台无警告信息。

#### Functional Requirements - 验收标准（按 FR 对应）

- AC-001（对 FR-001）：提供手绘卡通风格色彩清单（米黄/深蓝/木棕等）、字号层级（h1 手写体≥36px，其他楷体）、间距、圆角（12-24px）、多层阴影、动效时长（300-400ms）与弹性曲线的命名清单；组件的默认/悬停/按下/禁用/加载态在设计稿与文案规范中一一对应且可被走查。
- AC-002（对 FR-002）：在 360px、768px、1280px 视口下，无水平滚动；主要 CTA 在首屏内可见；容器最大宽度与边距符合规范表（审查样式或视觉走查）。
- AC-003（对 FR-003）：选择卡片具备高亮、辅助文案与禁用态；触发一次选择后其他选项进入禁用态，重复点击无二次提交（通过交互录屏验证）。
- AC-004（对 FR-004）：分数变化动画时长 0.8–1.2s；成就 Toast 单条展示约 3s，队列并发=1 严格串行，条与条之间最小间隔≥300ms；手绘卡通风格组件动效 300–400ms（进入/离开、悬停/按下采用弹性或标准曲线），位移≤16px，缩放≤5%，支持 wiggle/bounce 效果。
- AC-005（对 FR-005）：文本对比度自动化校验达到 AA；Tab 键可遍历主要可交互元素，焦点环可见并顺序合理（键盘测试与工具校验）。
- AC-006（对 FR-006）：提示/错误/分享等文案符合统一语气；不同结局类型出现差异化标题与描述（词库/样稿审阅）。
- AC-007（对 FR-007）：加载时出现骨架屏；错误时出现内嵌错误区块（含重试与“返回首页”）；空状态提供引导性文案与操作（功能走查）。
- AC-008（对 FR-008）：首版中文完成度 100%；提供文案清单与用词规范；对关键模块进行长度风险评估与截断策略走查。
- AC-009（对 FR-009）：提供手绘卡通风格色板（米黄、深蓝、木棕等）与字体示例（h1 手写体站酷快乐体，其他文字楷体霞鹜文楷）；主要页面具备装饰元素（回形针、标签纸等），列表页装饰简化；移动端字号≥16px（正文）、≥24px（标题），行距≥1.75；不提供深色主题与切换；示例页展示组件在浅色下的状态规范。
- AC-010（对 FR-010）：分享页不出现个人标识信息；内容审核失败时有面向用户的友好提示（用例演示）。
- AC-011（对 FR-011）：
  - 有数据时默认时间倒序；列表项目显示字段完整且对齐；
  - 采用无限滚动加载，接近底部时自动加载下一批次；
  - 接近底部 300px 以内触发加载；单批 items 数量=请求 limit（默认 20）；触发节流≥300ms；
  - API 超时≥10s 或错误时出现内嵌错误区块，重试后继续沿用 lastCursor 且无重复项；
  - 详情展示标题+摘要+逐步选择（含序号、选择文本、分数变化标签）；
  - 无数据时出现空状态插画/图标+引导按钮。
- AC-012（对 FR-012）：
  - 设计阶段提供至少 2 个视觉参考（截图/设计稿）；
  - 实施前完成设计对齐会议记录，明确配色、布局、组件标准；
  - 交付设计规范文档（色板、字体、间距等），可直接转为代码；
  - 关键页面（首页、游戏主页、场景页）有高保真设计稿或可交互原型。
- AC-013（对 FR-013）：
  - 每个页面的动效类型≤3 种，阴影层级≤2 层；
  - 无多色渐变（≥3 种颜色）使用；
  - 3D 变换、粒子效果等复杂装饰有明确业务说明；
  - 首次实施版本仅包含基础视觉（配色+布局+基础组件），复杂效果基于反馈决定。
- AC-014（对 FR-014）：
  - 实施前验证 PostCSS、Tailwind 配置文件存在且正确；

## 依赖与风险

### 技术依赖
- 依赖 AI 返回时延稳定性；若波动，应以骨架屏与队列化反馈缓冲。
- 依赖样式工具链（PostCSS、Tailwind CSS）配置正确；需在项目初期验证。
- 不同设备与浏览器的动效表现差异，需进行跨设备可用性验证。

### 设计依赖
- 文案与插画素材需要同步交付；如未就绪，采用占位风格与可替换机制。
- 视觉参考和设计规范需在实施前明确；模糊的设计需求会导致多次返工。

### 流程风险（基于实施经验）
- **视觉理解偏差**：仅凭文字描述可能导致实现方向偏离预期，需通过视觉参考和早期原型验证对齐；缓解措施：要求具体参考图片，实施前设计走查。
- **基础配置缺失**：缺少关键配置文件（如 `postcss.config.js`）可能导致样式完全不生效；缓解措施：项目初期使用测试页面验证工具链。
- **过度设计倾向**：追求技术复杂效果可能导致用户体验下降和开发浪费；缓解措施：从简单版本开始，基于反馈渐进增强。
- **迭代时间不足**：首次实现通常无法完美符合预期，需预留调整时间；缓解措施：项目规划中预留 30% 时间用于迭代。
- **技术债务积累**：开发过程中产生的测试文件和废弃代码如不及时清理会影响维护；缓解措施：完成时进行系统性清理并生成报告。

## 经验教训 (Lessons Learned)

### 实施过程总结 (2025-10-27)

本次 UI/UX 重设计经历了多次迭代才达到预期效果，过程中积累了以下关键经验：

#### 1. 视觉参考的必要性

**经验**：文字描述（如"手绘卡通风格"、"纸张质感"）无法准确传达视觉预期。

**教训**：
- ✅ **始终要求具体的视觉参考**：截图、设计稿、竞品示例等
- ✅ **避免仅依赖抽象描述**：即使是常见风格（卡通、扁平、拟物）也可能有不同理解
- ✅ **在实施前确认参考**：与用户对齐视觉标准，而非基于假设开始实施

**实际案例**：初期基于"手绘卡通"描述实现了立体木质边框、纸张纹理等元素，但用户不满意。直到提供了具体参考图片（温暖米黄背景 + 白色卡片 + 青色按钮 + 粗黑边框），才明确了真正的期望。

#### 2. 设计复杂度的权衡

**经验**：技术上先进的效果（3D 变换、粒子系统、复杂渐变）不一定等于好的用户体验。

**教训**：
- ✅ **优先简单清晰**：用户更看重布局、配色、按钮这些基础元素
- ✅ **警惕过度设计**：过多动效、渐变、阴影可能显得杂乱、"太亮"、"太花"
- ✅ **从简单开始迭代**：先实现基础视觉，再根据反馈增加装饰

**实际案例**：第二次尝试引入了"高级游戏 UI"（3D 卡片旋转、实时光晕、粒子系统），用户反馈"太亮"、"不需要渐变色"。最终采用的方案反而是最简单的：纯色背景 + 白色卡片 + 粗边框。

#### 3. 基础配置的优先验证

**经验**：样式不生效时，应先排查基础配置，而非反复修改样式代码。

**教训**：
- ✅ **检查工具链配置**：确认 PostCSS、Tailwind、CSS Modules 等工具正确配置
- ✅ **验证浏览器缓存**：使用硬刷新（Ctrl+Shift+R）排除缓存问题
- ✅ **创建测试页面**：用简单的测试样式（如 `border-8`）验证系统是否正常工作

**实际案例**：多次修改样式后发现边框、圆角等完全不显示。根本原因是缺少 `postcss.config.js` 文件，导致 Tailwind CSS 无法编译。创建该文件后所有样式立即生效。

#### 4. 用户反馈的价值

**经验**：用户的"不满意"反馈虽然模糊，但是定位问题的关键线索。

**教训**：
- ✅ **重视所有反馈**：即使是"效果太差"这样的模糊反馈也需认真对待
- ✅ **主动请求澄清**：询问具体不满意的部分（配色？布局？按钮？）
- ✅ **请求视觉参考**：当文字描述不清晰时，主动请求截图或参考图片
- ✅ **验证理解是否一致**：通过截图、预览链接确认双方看到的是同一效果

**实际案例**：用户连续反馈"没有达到预期"、"效果太差"、"没有实现"。通过多轮对话和提供参考图片，才定位到配置问题和视觉方向偏差。

#### 5. 迭代式实施的必要性

**经验**：复杂的视觉改造不可能一次到位，需要接受多次迭代调整。

**教训**：
- ✅ **预留调整时间**：初次实现不太可能完美符合预期
- ✅ **快速原型验证**：尽早展示可交互原型以收集反馈
- ✅ **保持灵活性**：准备好推翻之前的方案，基于反馈重新设计
- ✅ **记录废弃方案**：保留实施报告以避免重复尝试失败方案

**实际案例**：本次共经历了三个版本：
1. 早期卡通风格（立体木框 + 纸张纹理）→ 废弃
2. 高级游戏 UI（3D 效果 + 粒子）→ 废弃  
3. 简洁温暖风格（参考图片指导）→ 成功

#### 6. 清理与维护的重要性

**经验**：开发过程中的测试文件、调试代码、废弃组件需要及时清理。

**教训**：
- ✅ **完成后立即清理**：删除测试页面、调试工具、废弃组件
- ✅ **记录清理内容**：生成清理报告以备查
- ✅ **检查 404 错误**：清理未使用的静态资源引用
- ✅ **保持代码库整洁**：便于后续维护和新人理解

**实际案例**：完成实施后清理了 10+ 个测试文件、3 个废弃组件、未使用的纹理文件、过时的实现报告，以及修复了字体文件的 404 错误。

### 未来实施建议

基于本次经验，对未来的 UI/UX 改造项目提出以下建议：

1. **启动阶段**：
   - 要求用户提供 2-3 个具体的视觉参考（截图、竞品、设计稿）
   - 确认基础工具链配置完整（PostCSS、Tailwind 等）
   - 创建简单测试页面验证样式系统工作正常

2. **实施阶段**：
   - 从最简单的版本开始（配色 + 布局 + 基础组件）
   - 尽早展示可交互原型收集反馈
   - 避免在未确认方向前投入过多时间在复杂效果上

3. **验证阶段**：
   - 与用户确认截图或预览链接，确保双方看到相同效果
   - 使用硬刷新排除浏览器缓存问题
   - 记录用户的具体反馈点（而非泛化的"不满意"）

4. **完成阶段**：
   - 清理所有测试文件和废弃代码
   - 修复控制台警告和 404 错误
   - 生成清理报告和实施文档
